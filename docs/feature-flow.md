# 叙光 Novel Studio：核心创作流

## 功能名

从 Idea 到可审查章节的独立创作工作台，并支持按阶段路由到不同 API 服务渠道。

## 用户任务

作者打开产品后，不需要理解文件或旧编译器，直接知道今天要推进什么；需要 AI 时，可以先维护多个 OpenAI Chat Completions 兼容的 API 服务渠道，再为 Idea、逻辑、蓝图、写作、审查分别选择“API 渠道 + 模型 ID”。

## 进入条件

- 服务端已启动。
- 未配置模型时仍可编辑和保存，但 AI 主动作明确阻塞并在当前应用内打开配置抽屉。
- 模型配置允许只保存部分渠道或阶段路由，未完成的阶段单独显示阻塞。

## 退出条件

- 当前阶段产物已保存到独立 Workspace。
- 用户清楚下一阶段是什么。
- AI 结果永远先进入建议稿，不自动覆盖已确认内容。
- 每次模型运行都能追溯到实际使用的 API 渠道与模型。

## 主流程

1. 今日工作台：确认当前作品、当前阶段、唯一下一步。
2. 模型配置：添加一个或多个 API 服务渠道，填写名称、Base URL 与渠道 API Key。
3. 阶段路由：为五个职责分别选择 API 渠道并填写模型 ID。
4. Idea：输入原始灵感，形成高概念、读者承诺、差异点和待验证缺口。
5. 故事引擎：建立欲望、阻力、代价、升级链和长线悬念。
6. 蓝图：形成作品定位、角色关系、卷纲和下一章契约。
7. 写作：只按已确认章节契约生成或编辑候选正文。
8. 审查：诊断阻塞问题、节奏、逻辑、AI 痕迹并由作者采纳。

## 模型配置流程

1. 打开“模型配置”抽屉。
2. 在“API 服务渠道”区添加、选择或移除渠道。
3. 编辑当前渠道的名称、Base URL、API Key；已保存密钥保持脱敏，留空继续沿用。
4. 在“阶段路由”区为每个职责选择 API 渠道并填写模型 ID。
5. 可对当前选中的渠道执行连接测试；测试模型取该渠道已绑定的第一个阶段模型。
6. 点击唯一主动作“保存配置”，服务端按渠道 ID（providerId）保留未重新输入的密钥并持久化全部路由。

## 分支流程

| 情况 | 去哪里 | 用户看到什么 | 写入什么账本 |
|---|---|---|---|
| 模型未配置 | 当前页配置抽屉 | 当前阶段缺少渠道、密钥或模型 | `.data/settings.json` |
| 新增渠道 | 配置抽屉 · API 服务渠道 | 新渠道编辑表单与未配置状态 | 保存后写入 `providers[]` |
| 阶段切换渠道 | 配置抽屉 · 阶段路由 | 每个阶段独立的 API 渠道选择和模型 ID | 保存后写入 `routes` |
| 渠道连接失败 | 配置抽屉 | 当前渠道、模型与错误信息 | 不写入 Workspace |
| AI 调用失败 | 当前阶段错误卡 | API 渠道、状态码、可重试动作 | Workspace 最近运行记录 |
| 上游内容变化 | 当前阶段 | 下游产物标记为需重新确认 | Workspace stale 状态 |
| 审查有阻塞 | 审查页 | P0/P1 问题和修改建议 | review findings |

## 状态

- 未开始：没有该阶段产物。
- 进行中：作者编辑或 AI 正在运行。
- 待确认：AI 建议已返回，等待作者确认。
- 已完成：作者已确认，下一阶段解锁。
- 阻塞：当前阶段缺少有效的 API 渠道路由、上游确认或调用失败。

## 风险

| 优先级 | 风险 | 如何展示 | 如何处理 |
|---|---|---|---|
| P0 | 任一渠道 API Key 暴露到浏览器 | 前端只返回每个渠道的 `hasApiKey/apiKeyMasked` | 密钥仅服务端保存和调用 |
| P0 | 路由引用已删除渠道 | 保存时服务端拒绝无效 providerId | 删除渠道时前端同步清空相关路由 |
| P0 | AI 覆盖作者确认内容 | 建议稿与确认稿分区 | 必须点击确认采用 |
| P1 | 阶段实际使用渠道不透明 | 最近运行展示 API 渠道与模型 | 运行记录写入 providerId/providerName/model |
| P1 | 上游改动导致下游过期 | 页面顶部琥珀色状态 | 重新生成或人工保留 |
| P1 | 页面动作过多 | 保存配置是唯一主动作 | 添加、移除、测试为次动作 |

## 主动作

- 创作页：当前阶段唯一的“生成 / 确认 / 继续”动作。
- 模型配置抽屉：保存全部 API 渠道与阶段路由。

## 次动作

- 添加渠道
- 移除渠道（保存前可撤销）
- 测试当前渠道
- 保存草稿
- 查看历史
- 导出 Workspace

## 完成后写入

- `.data/settings.json`：多渠道凭据与阶段路由。
- `.data/workspace.json`：创作状态与最近运行摘要。
- `.data/runs/*.json`（后续扩展）。

## v0.2：真实项目日更流（第一阶段）

### 用户任务

已有小说作者打开工作台后，不再重复建立作品，而是从磁盘中的正式项目恢复当前书、当前章、当前阶段、风险和唯一下一步。

### 任务路径

1. 服务端只读扫描小说库根目录，识别同时包含 `正文/`、`大纲/`、`设定/`、`追踪/` 的项目。
2. 顶部项目切换器列出已识别项目；选择项目后加载该项目仪表盘。
3. 今日工作台优先读取 `追踪/progress.json` 与 `追踪/今日工作台.md`。
4. 当前章优先读取 `progress.current_chapter`，并关联 `大纲/章节契约/第XXX章.md` 与已存在正文。
5. 风险优先读取 `progress.open_risks`，并区分阻塞、警告和提示。
6. 当前唯一主动作由项目状态决定：没有章节契约时补契约；已有契约且无正文时开始写作；已有正文时进入审查。
7. 第一阶段对正式项目保持只读，原有 `.data/workspace.json` 继续承载 AI 候选稿和未确认编辑状态。

### 《苟成仙帝，出关即无敌》验收场景

- 当前书：苟成仙帝，出关即无敌。
- 当前章：第 4 章。
- 已完成章节：1、2、3。
- 当前阶段：预写完成，待正式写草稿。
- 主动作：开始写第 4 章。
- 页面显示第 004 章契约已就绪，并展示旧编译流冲突风险。

### 安全边界

- 项目发现只允许发生在配置好的小说库根目录内。
- 浏览器不接收任意绝对路径，只接收服务端生成的项目 ID。
- 第一阶段 API 只读，不写入 `正文/`、`设定/`、`大纲/`、`追踪/`。
- 未来写回必须先生成差异，作者确认后原子写入并产生 checkpoint。

## v0.3：多厂商模型中心与章节校准台

### 用户任务路径

1. 从项目今日工作台进入“模型中心”，先选择厂商预设，而不是把所有密钥塞进同一个品牌输入框。
2. 每个厂商实例独立维护协议、Base URL、API Key；密钥只存服务端。
3. 在章节工作区进入“模型校准”，选择 2—4 个“厂商 + 模型”候选。
4. 系统读取当前章正式契约、硬规则、上下文和 P0 风险，向所有候选发送同一份匿名校准任务。
5. 校准结果只进入 `.data/calibrations/`，按契约达成、自然度、钩子、边界和耗时并排展示，不进入正式正文。
6. 作者据此把逻辑、正文、审查、改写职责路由到不同厂商模型。

### 厂商配置流程

- 预设：第三方中转、OpenAI 官方、DeepSeek 官方、Anthropic 官方、Gemini 官方。
- “厂商”负责密钥和协议；“模型路由”只引用厂商实例和模型 ID。
- 选择预设时可填充协议与 Base URL，但不得覆盖已输入的 API Key。
- 第三方中转统一使用 OpenAI Compatible 协议，第三方 Key 必须填在该中转实例中。

### 模型校准流程

- 进入条件：真实项目、当前章契约、至少两个已配置候选模型。
- 主动作：运行本章校准。
- 输出：每个候选的匿名编号、厂商、实际模型、延迟、使用量、结构化试写或逻辑方案、错误状态。
- 安全边界：校准不写 `正文/`、`设定/`、`大纲/`、`追踪/`；失败候选不影响其他候选。
- 退出条件：作者能据结果确定或调整章节职责路由。

### 页面顺序

`今日工作台 → 第N章工作区 → 模型校准 → 候选正文 → 审查定稿 → 差异确认 → 正式写回`

## v0.4：章节候选稿—审查—作者确认闭环

### 任务路径

1. 进入当前章工作区，服务端按“项目 ID + 章节号”读取独立候选账本。
2. 作者可手写并保存候选稿，或调用写作路由生成候选正文；两者都只写入 `.data/project-chapters/`。
3. 候选稿存在后进入审查页，审查模型只返回 Finding、评分和建议，不直接改写正文。
4. 作者根据 Finding 回到候选稿修改，或确认当前候选版本。
5. “确认候选”只把该版本标记为可写回，不直接创建或覆盖 `正文/`。
6. 后续正式写回必须经过差异预览、作者再次确认和 checkpoint。

### 主动作状态

- 无候选稿：生成本章候选稿。
- 有未保存编辑：保存候选稿。
- 已保存候选稿：进入审查。
- 审查未运行或候选变化：运行只读审查。
- 审查完成：确认候选版本。
- 已确认：准备差异预览（本阶段只显示就绪，不写正式文件）。

### 安全边界

- 写作和审查读取同一份正式章节契约与正式事实。
- AI 生成结果可以持久化到侧车候选账本，但不能写入正式项目目录。
- 审查角色禁止返回替换稿，候选正文变更后旧审查自动标记过期。
- 作者确认绑定候选文本哈希；文本再次修改后确认失效。

## v0.5：正式写回前差异预览、checkpoint 与追踪同步

### 用户任务

作者已经完成当前章候选稿、只读审查和候选版本确认后，需要在**一次正式写入发生前**看清：将创建或修改哪些正式文件、每个文件为什么变化、变化后的内容是什么，以及失败时如何恢复。

### 任务路径

1. 从“审查定稿”进入“写回预览”。
2. 服务端校验候选哈希、审查哈希、作者确认态和 P0 数量。
3. 点击唯一主动作“生成追踪同步提案”；模型只提取章节摘要、角色变化、伏笔推进、时间线事件和下一章恢复包，不改写章节正文。
4. 服务端以正式文件当前内容为基线，生成章节正文与各追踪账本的完整 after 文本，并记录每个 source hash。
5. 页面按“新增正文 / 更新追踪 / 追加运行记录”分层展示文件差异；默认只显示摘要，可展开 before/after。
6. 作者勾选“我已核对全部正式文件”，再点击“创建 checkpoint 并正式写入”。
7. 服务端再次校验 candidate hash、review hash、plan hash 与全部 source hash。
8. 服务端先在 `.data/writeback-checkpoints/` 创建包含 manifest 与原文件快照的 checkpoint，再使用临时文件执行多文件写入；任一写入失败即按快照回滚。
9. 写入成功后，章节侧车账本标记为 committed；页面显示 checkpoint ID、实际文件清单和 `formalWritePerformed = true`。
10. 重新读取项目 dashboard，进入下一章的“今日工作台”；若下一章契约缺失，唯一下一步是先补契约。

### 正式写入目标

- `正文/第N章 标题.md`：来自作者已确认的候选文本，不经同步模型改写。
- `追踪/progress.json`：把当前章加入 completed，当前章推进到 N+1，下一步指向下一章契约。
- `追踪/今日工作台.md`：从“写当前章”切换为“恢复并准备下一章”。
- `追踪/上下文.md`：追加本章完成恢复包。
- `追踪/角色状态.md`：追加本章角色状态变化。
- `追踪/伏笔.md`：追加本章伏笔新增、推进或回收。
- `追踪/时间线.md`：追加本章已发生事件。
- `追踪/章节摘要.jsonl`：追加一条结构化章节摘要。
- `追踪/诊断.md`：追加当前确认版本的审查归档；没有 Finding 时也记录“无阻塞 Finding”。
- `追踪/checkpoints.jsonl`：追加正式写回 checkpoint 记录。

### 分支流程

| 情况 | 阻塞位置 | 处理 |
|---|---|---|
| 候选未确认 | 写回预览入口 | 返回审查定稿完成确认 |
| 当前审查过期 | 生成提案前 | 返回候选稿并重新审查 |
| 仍有 P0 | 生成提案前 | 禁止写回，回到候选稿修复 |
| 同步模型未配置 | 生成提案 | 打开模型配置；使用 review 路由 |
| 同步提案生成失败 | 写回预览 | 不创建或修改正式文件，可重试 |
| 提案生成后候选变化 | 写回预览 | plan 标记 stale，必须重新生成 |
| 正式文件在预览后被外部修改 | 最终提交 | source hash 冲突，拒绝写入并刷新预览 |
| checkpoint 创建失败 | 最终提交 | 不执行正式写入 |
| 任一文件写入失败 | 最终提交 | 自动回滚所有已变更文件并返回错误 |
| 正式章节文件已存在 | 生成提案 | 默认阻塞，禁止无提示覆盖现有正文 |

### 页面主动作

- 没有提案：`生成追踪同步提案`。
- 提案已就绪且未核对：主按钮不可用，提示先核对全部文件。
- 已核对：`创建 checkpoint 并正式写入`。
- 已提交：`进入下一章今日工作台`。

### 安全不变量

- 同步模型永远收不到写文件能力，只返回结构化元数据。
- 章节正文 after 文本必须逐字来自已确认候选；模型不得改写。
- 预览阶段 `formalWritePerformed = false`。
- 最终提交必须同时满足 candidate/review/confirmation/plan/source 五层哈希一致。
- checkpoint 成功落盘之前，不得触碰正式项目文件。
- 正式写入发生后必须刷新 dashboard，不能继续把旧章节当成当前任务。

## v0.6：下一章章节契约门禁

### 用户任务

正式写回把进度推进到第 N+1 章后，作者需要先把“这一章写什么、必须发生什么、禁止发生什么、章末钩子是什么”固化为正式章节契约，才能进入候选正文。

### 进入条件

- 已选择真实小说项目。
- dashboard 指向当前章。
- 当前章正式章节文件不存在。
- 当前章正式契约存在时进入只读状态；不存在时进入契约草稿状态。

### 主流程

1. 今日工作台发现 `chapter.contractReady = false`，唯一主动作改为“补第 N 章契约”。
2. 进入章节契约页，服务端读取正式规则、上下文、角色、伏笔、时间线和今日任务；这些文件只读。
3. 作者手写契约，或使用逻辑模型生成一个侧车提案；结果只进入当前章 `.data/project-chapters/`。
4. 保存后执行确定性结构检查：本章目标、读者情绪、必须发生、禁止发生、章末问题、字数与节奏六个区块必须齐全。
5. 结构合格后生成单文件正式差异预览；此时不写 `大纲/`。
6. 作者核对完整 after 文本并勾选明确确认。
7. 服务端再次校验 revision、草稿 hash、计划 hash 与目标文件 source hash。
8. 在 `.data/contract-checkpoints/` 创建 checkpoint，再创建 `大纲/章节契约/第NNN章.md`。
9. dashboard 重新加载，`contractReady = true`；唯一主动作变为“进入候选正文”。

### 分支

| 情况 | 页面行为 | 正式写入 |
|---|---|---|
| 正式契约已存在 | 只读展示正式契约与路径 | 无 |
| 草稿为空 | 展示结构模板和恢复上下文 | 无 |
| 结构缺失 | 标红缺失章节，主动作仍为保存 | 无 |
| 预览后草稿变化 | 计划自动 stale，必须重新预览 | 无 |
| 目标契约被外部创建/修改 | source conflict，拒绝提交 | 无 |
| 提交成功 | 展示 checkpoint 与候选正文入口 | 仅创建一个正式契约文件 |

### 页面唯一主动作

- 正式契约已存在：进入候选正文。
- 草稿有未保存修改：保存章节契约草稿。
- 草稿已保存但结构不完整：继续补齐契约。
- 草稿合格且未预览：生成正式差异预览。
- 预览已就绪：创建 checkpoint 并写入正式契约。
- 提交完成：进入候选正文。

### 安全边界

- 模型只生成侧车契约草稿，不得声称写入正式大纲。
- 正式目标固定为当前章 `大纲/章节契约/第NNN章.md`，不接受客户端路径。
- 已存在正式契约时禁止覆盖；修改旧契约另走返工流程。
- 契约提交不写正文、不推进 progress、不修改任何追踪账本。

## v0.7：候选正文生成任务包与费用确认

### 用户任务

作者已经有正式章节契约并配置了写作模型，但在真实产生费用前，需要先看清本次调用使用哪个厂商/模型、读取哪些正式事实、必须达成什么、有哪些风险，以及输出仍会落在哪一层。

### 任务路径

1. 当前章正式契约就绪、候选正文为空时，唯一主动作是“检查生成任务包”，此动作不调用模型。
2. 页面展开生成任务包，展示写作路由、正式契约路径、今日必达目标、风险数量、侧车目标和“不写正式正文”边界。
3. 作者明确勾选“本次调用会产生厂商费用，并只生成侧车候选”。
4. 唯一主动作变为“确认调用模型生成候选”。
5. 客户端提交当前章节 revision 与 `confirmModelSpend = true`；服务端在进入模型调用前强制校验该字段。
6. 模型结果只写入 `.data/project-chapters/` 的 candidate；页面回到候选编辑态。
7. 已有候选时，“重新生成候选”只打开同一任务包，不直接调用模型；未保存手写修改时禁止进入重新生成。

### 状态与失效

- 路由厂商或模型变化：已打开的任务包自动关闭，必须重新核对。
- 章节 revision 变化：服务端按现有乐观锁拒绝旧任务包。
- 正式契约缺失：仍由 `WRITER_CONTRACT_REQUIRED` 阻塞。
- 未明确费用确认：服务端返回 `MODEL_SPEND_CONFIRMATION_REQUIRED`，不得发出上游请求。
- 模型失败：保留原候选和手写内容，不创建正式文件。

### 页面唯一主动作

- 无候选、任务包关闭：检查生成任务包。
- 任务包已打开但未确认费用：确认项未勾选，主动作禁用。
- 任务包已确认：确认调用模型生成候选。
- 候选有未保存修改：保存当前候选版本。
- 候选已保存：进入只读审查。

### 安全边界

- “检查生成任务包”完全在前端完成，不产生模型调用与费用。
- 服务端不信任按钮状态，必须收到显式 `confirmModelSpend = true`。
- 生成任务包只展示来源摘要与路由元数据，不向前端暴露 API Key。
- 生成结果仍是侧车参考层，正式正文写回继续受审查、作者确认、差异预览和 checkpoint 保护。

## v0.8：正文生成主链路

### 目标

把“有契约”收敛成可执行、可诊断的章节生产链路：**正式事实 + 上一章正文 + 当前章正式章节契约 → 生成任务包 → 结构化章内节拍 + 完整候选正文 → 确定性质量门禁 → 定向重写或只读审查**。本阶段优化的是内容闭包、候选质量和返工路径；token 估算与计费提示仅保留为次级运行信息，不作为页面主目标或流程状态。

### 输入与分层

- 正式事实：`设定/`、正式大纲与 `追踪/` 中当前章确需的只读事实，按路径和 hash 固定快照。
- 上一章正文：读取最近一章正式 `正文/` 全文，承担语气、场景和未完动作的直接续接。
- 章节契约：当前章正式契约，是目标、禁区、爽点和章末钩子的硬约束。
- 侧车候选：任务包、章内节拍、完整候选、重写版本与运行记录，只写 `.data/project-chapters/`。
- 诊断：确定性门禁结果与审查 Finding，单独展示和持久化，不晋升为正式事实。

### 主流程

1. 服务端按当前章组装任务包，记录正式事实清单、上一章正文、章节契约及各自 source hash；缺任一必需输入时直接阻塞。
2. 作者核对任务包后，唯一主动作是“生成本章候选”；任务包一旦进入运行即按 hash 冻结，不在生成中静默换源。
3. 写作模型一次返回结构化章内节拍和完整候选正文；节拍至少包含顺序、场景目标、冲突/转折、情绪或爽点、预计字数和契约目标映射。
4. 服务端先校验返回结构，再把节拍与完整候选原子写入侧车；失败时保留上一版候选。
5. 不调用模型，立即运行确定性质量门禁：输入 hash、结构完整、契约必达项覆盖、禁写项、字数区间、节拍顺序/字数合计、正文非空与章末钩子。
6. 全部通过进入 `candidate_ready`；作者可进入只读审查。
7. 任一硬门禁失败进入 `candidate_blocked`，页面只给出可定位到节拍/段落的阻塞项，唯一主动作是“按阻塞项定向重写”。
8. 定向重写携带原任务包 hash、原候选 hash 和选中的阻塞项；模型仍返回更新后的完整节拍与完整候选，随后重新跑全部确定性门禁。
9. 作者手改后进入 `dirty`；保存时重新计算 hash 并重跑门禁。只有门禁通过的版本可送审，审查完成且 candidate hash 一致时进入 `review_ready`。

### 分支与唯一主动作

| 状态 | 页面唯一主动作 | 说明 |
|---|---|---|
| `generating` | 正在生成… | 禁止重复提交；可保留次级取消入口 |
| `candidate_ready` | 进入只读审查 | 确定性门禁已通过 |
| `candidate_blocked` | 按阻塞项定向重写 | 不允许绕过硬门禁直接送审 |
| `dirty` | 保存并重新检查 | 保存候选后重跑全部门禁 |
| `review_ready` | 查看审查并决定 | 审查只产出 Finding，不改正文 |

### 安全边界

- 初次生成和定向重写都只更新侧车节拍与完整候选，不创建、覆盖或追加正式 `正文/`。
- 正式事实、侧车候选、诊断结果三层必须使用不同标签和视觉权重；诊断不得反向改写正式事实。
- 质量门禁是版本化的确定性规则，不依赖模型自评；规则版本或候选 hash 变化后旧结果自动失效。
- 定向重写不做无来源的局部拼接；保存的是一份可独立审查的完整候选，并保留前一版本用于比较。
- 正式正文仍只能沿用后续“作者确认 → 差异预览 → checkpoint → 正式写回”链路产生。

## v0.9：开书重建——从 Idea 开始

### 用户任务

作者以《苟成仙帝，出关即无敌》为打磨样例，但当前目标不是续写既有第 4 章，而是从最初 Idea 重新确认作品承诺，并依次完成故事引擎、小说蓝图、第一章写作与审查。

### 进入条件

- Workspace 已创建，允许保留作品名和一条未经确认的原始灵感。
- 所有下游阶段均为未开始；不得因为磁盘中存在既有正文而自动跳转日更工作台。
- 已发现的正式项目仅作为“续写已有正文”的次级入口，不改变开书重建的默认任务。

### 主路径

1. 首页进入“开书工作台”，显示当前书、当前阶段 Idea、风险和唯一下一步。
2. 作者确认作品名、类型、目标读者、语气与原始灵感。
3. 进入 Idea 工作台；模型只生成高概念、读者承诺、差异点和待验证问题的候选。
4. 作者确认 Idea 后，依次解锁故事引擎与小说蓝图。
5. 蓝图确认后，当前章节从第 1 章开始；蓝图中的章节候选先复制为“待确认当前章契约”，作者单独确认后才进入章节候选生成、只读审查和作者确认。
6. 当前章的契约、正文和审查均由作者确认后，作者可归档本章并准备下一章；归档只追加 Workspace 历史，下一章仍先停在待确认契约。
7. 既有正式项目的第 4 章续写，通过作品切换器中的“续写已有正文”显式进入；返回“开书重建”不删除任何正式文件或侧车账本。

### 唯一主动作

- 首页：`开始打磨 Idea`。
- Idea：无模型配置时为 `保存作者输入`；模型可用时为 `生成 Idea 建议`；有建议时为 `确认并进入故事引擎`。
- 续写模式：沿用既有章节契约 → 候选正文 → 审查 → 写回流程。

### 安全边界

- 开书重建默认只写 `.data/workspace.json`，不改动 `正文/`、`设定/`、`大纲/`、`追踪/`。
- 切换到续写已有正文必须是作者显式动作。
- 从续写返回开书重建不清空候选、不覆盖正式事实，也不自动同步两套状态。
- 连续写作归档的 `formalWritePerformed = false`；它不是正式正文写回，也不会隐式创建正式项目。

### 连续章节推进

```text
蓝图已确认
  -> 当前章契约候选（建议）
  -> 作者确认当前章契约
  -> 当前章候选正文（建议）
  -> 作者确认正文
  -> 只读审查（建议）
  -> 作者采纳审查
  -> 归档当前章（Workspace history append-only）
  -> 下一章契约候选（建议）
```

- Writer 在新版 Workspace 中只能读取 `currentChapter.contract.confirmed`，不得把蓝图内的 `nextChapterContractCandidate` 直接当作当前章事实。
- 章节历史保存确认契约、确认正文、确认审查的不可变快照；后续编辑只能作用于当前章运行态。
- 旧 Workspace 缺少 `chapterCycleVersion` 时维持旧蓝图契约兼容路径；首次完成当前章时才迁入连续章节状态。

## v1.0：Idea 多轮打磨与版本确认

### 用户任务

作者拿到第一版 Idea 建议后，不应被迫在“直接确认”与“整份推翻”之间二选一，而要围绕金手指机制、闭关外爽点、主角动机、长线悬念和免费向开篇持续提出反馈，直到当前版本足以承担整本书的上游契约。

### 主路径

1. 作者输入原始灵感并生成第 1 版完整 Idea 工作稿。
2. 页面保留当前可编辑工作稿，同时提供“本轮反馈”输入区。
3. 作者明确本轮要保留、推翻和继续深挖的内容；模型基于当前版本与最近版本历史生成一份完整替代稿，而不是零散点评或补丁。
4. 新结果成为当前工作稿，上一版进入只读版本历史；作者可继续反馈、手工修改或恢复旧版本。
5. 每轮生成都记录版本号、产生该版本的反馈、模型来源与时间，不覆盖历史版本。
6. 只有作者主动选择“确认当前版本为 Idea 定稿”后，才锁定 `confirmed` 并解锁故事引擎。

### 分支与恢复

- 当前稿被手工修改后再打磨：先把手工修订后的完整稿保存为一个作者版本，再生成下一版。
- 模型调用失败：保留当前稿、反馈和全部历史，允许原地重试。
- 恢复旧版本：只把其内容复制为当前工作稿，不删除后续历史，也不自动确认。
- 第 1 版即满意：允许直接确认，但确认是明确的次级动作，不再由全局底栏默认触发。

### 页面唯一主动作

- 有建议稿且反馈为空：主动作“填写本轮反馈”；确认当前版本是次级动作。
- 有建议稿且反馈完整：主动作“按反馈继续打磨一版”。
- 正在生成：主动作显示“正在打磨下一版”并禁用。
- 模型失败：主动作“重试本轮打磨”。

### 安全边界

- 每轮只更新 Idea 侧车候选与版本历史，不写入故事引擎、蓝图、正文或正式追踪。
- 模型必须返回完整 Idea 候选，不得替作者确认、不自动推进阶段。
- 确认时冻结的是当前编辑器中的完整内容；版本历史只作为恢复与比较依据。
